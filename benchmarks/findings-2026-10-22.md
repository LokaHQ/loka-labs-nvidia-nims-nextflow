## 1. MSA Search NIM

### What was done

| | |
|---|---|
| `909b65f` | MSA Search client added (`bin/msa_search_nim.py`), msa-search image version recorded |
| `80edd9f` | Four diagnostic workflows added to isolate the start-up failure |
| `d5eeb48` | Entrypoint fix; `OPENFOLD3_MSA` now takes `params.msa_nim_url` |

### The issue

The `msa-search` image was the only NIM that never received the `ENTRYPOINT []`
change applied to `rfdiffusion-nim` and `proteinmpnn-nim` in September. Its own
entrypoint started the server using the image's baked-in empty `NGC_API_KEY`
before the Nextflow task script — which fetches the real key from Secrets
Manager — ever ran. Every artifact request then failed authentication.

This presented as an NGC entitlement problem and was diagnosed as one for some
time. It was not. Evidence that ruled entitlement out:

- `nim/ipd` artifacts downloaded with the same key; `nim/colabfold` did not.
- Direct HTTPS and the NGC SDK both reached the colabfold artifacts with that
  key, returning HTTP 200.
- The failure reproduced with both a personal and a service key, on NIM 1.0.0
  and 2.6.0.

Only `nimlib` refused the artifacts, which located the fault in the token
exchange, not the entitlement.

### Fix and verification

`assets/nim_entrypoint_fix/Dockerfile.msa-search`, pushed to ECR as tag
`msa-search-updated`. Authentication succeeds and databases download.

### Measurement

NVIDIA's hosted MSA endpoint returned a **5,317-sequence MSA in 2.7 s**.
MSA generation is therefore not a bottleneck in the pipeline, and was not
blocking the benchmark — only the self-hosted container path was blocked.

### Open item

The self-hosted MSA NIM ships no databases and pulls **~1.4 TB** into
`NIM_CACHE_PATH` on first start. Batch volumes are ephemeral and the
`gpu-standard` environment provides 200 GB, so it cannot run as a per-job
container. Not yet resolved.

## 2. RFdiffusion — NIM vs no-NIM

### What was done

Both containers were run **standalone through raw AWS Batch, with no Nextflow
involved**, to remove the orchestrator as a variable.

| | |
|---|---|
| Containers | `rfdiffusion-nim-code-updated` (no-NIM), `rfdiffusion-nim` (NIM) |
| Driver | no-NIM: upstream `run_request.py`. NIM: HTTP to `/biology/ipd/rfdiffusion/generate` |
| Seeds | 0, 5, 34 |
| Per seed | 1 warmup + 3 repeats |
| Input PDB | byte-identical both sides, SHA-256 `470cef3a190a9f0f4d1d7b14f7cce080e3b26f323d334e2ae35e3133e68895eb` |
| Contigs | `A18-132/0 78-78` (binder length 78) |
| Hotspot | `A56` |
| Diffusion steps | 50 |
| Hardware | 1 GPU, 4 vCPU, 24 GB, queue `nvidia-nims-gpu-standard` |

Confirmed from the NIM server log that all 12 requests ran 50 timesteps, so the
two sides are compared on identical parameters.

### Timing

| | first call | steady state |
|---|---|---|
| no-NIM | **1851.5 s** | 9.4 s |
| NIM | **17.1 s** | 9.8 s |

no-NIM per-seed detail (sampling time):

| seed | warmup | repeat 00 | repeat 01 | repeat 02 |
|---|---|---|---|---|
| 0 | 1851.5 s | 9.4 s | 9.4 s | 9.5 s |
| 5 | 13.4 s | 9.4 s | 9.5 s | 9.5 s |
| 34 | 13.5 s | 9.4 s | 9.4 s | 9.4 s |

The 1851.5 s is confined to the first call in a fresh container. The cause is
TensorRT engine compilation: the no-NIM container compiles engines locally on
first use, producing a **440 MB / 2,464-file** cache. The NIM downloads
prebuilt `.trt` engines from NGC (`Base_ckpt/*.trt`, `Complex_base_ckpt/*.trt`)
and compiles nothing.

Steady-state inference speed is the same within ~4%.

### Structure — do the two arms produce the same design?

Each seed was run through **both** containers. The two resulting binders were
superposed on the target chain (Kabsch) and compared, Cα by Cα.

| seed | no-NIM gives | NIM gives | difference between them |
|---|---|---|---|
| 0 | a binder, reproducible | a binder, reproducible | **2.81 Å** |
| 5 | a binder, reproducible | a binder, reproducible | **3.15 Å** |
| 34 | a binder, reproducible | a binder, reproducible | **14.21 Å** |

"Reproducible" is literal — see Determinism below. Neither arm is wandering
between runs, so the difference column is the difference between the two
implementations, not noise.

The target chain is not designed, so it should be unchanged between the arms.
It is: 0.0086, 0.0168 and 0.0208 Å. That confirms the superposition is correct
and the difference above comes from the binder itself.

### How big is 2.81 Å?

RMSD has no meaning without a reference. For scale, on this system:

| Distance | What it corresponds to |
|---|---|
| 0 Å | the identical structure |
| ~1.5 Å | the length of one chemical bond |
| ~3.8 Å | the spacing between neighbouring Cα atoms along a backbone |
| **2.81 – 3.15 Å** | **NIM vs no-NIM, seeds 0 and 5** |
| **14.21 Å** | **NIM vs no-NIM, seed 34** |
| 15.8 – 30.9 Å | two deliberately unrelated designs |

The last row is measured, not assumed: two *different* seeds run through the
*same* container, which by design should share nothing. Doing that within the
NIM gives 28.62 / 27.56 / 15.84 Å, and within no-NIM 27.87 / 30.89 / 20.77 Å
for seed pairs 0-5, 0-34 and 5-34. That also confirms both implementations
respond to the seed rather than ignoring it.

Reading the main table against this scale: seeds 0 and 5 put the two arms in a
similar region — under one residue's spacing apart, same overall shape, but
distinguishable structures. Seed 34 at 14.21 Å is roughly half the distance
between two unrelated designs, which is a different binder rather than a
shifted one.

### Determinism

Both implementations are deterministic at a fixed seed.

| | within a run | across separate container instances |
|---|---|---|
| no-NIM | 3 repeats byte-identical | not tested |
| NIM | 4 calls byte-identical (SHA-256) | byte-identical, all 3 seeds |

The NIM was run twice on separate Batch jobs and separate GPU instances; seeds
0, 5 and 34 each reproduced the same output PDB bit-for-bit. Different seeds
produce different structures in both implementations.

So the 2.81 / 3.15 / 14.21 Å gap between implementations is not run-to-run
noise. Each side is stable; they are stably different.

## Prior related finding

A previous investigation
(`benchmarks/rfdiffusion-reproducibility-investigation.html`) verified via
blake3 checksum that the NIM and OSS RFdiffusion carry byte-identical trained
weights (`Base_ckpt.pt`). The divergence is therefore not a weights or seeding
difference.

## Not measured

- Whether a TensorRT cache warmed at one binder length is reusable at another.
  The cross-length arm of the cache test was stopped before it reported.
- Anything at the N=100 scale. All numbers above are from N=3 seeds.
