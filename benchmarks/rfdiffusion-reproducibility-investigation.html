RFdiffusion Reproducibility Investigation: NIM vs. OSS

Troubleshooting log, not a benchmark result. Target: PD-L1 binder design, 78-residue binder, [A18-132/0 78-78] contig, hotspot A56, same input on both sides throughout. Companion to the main NIM-vs-no-NIM benchmark doc.

1. Purpose

Can RFdiffusion be made to produce the same design across the NIM and open-source (OSS) implementations, given the same seed — and if not, why not, specifically and verifiably rather than by assumption? One day was budgeted for this.

3. Static checks

3.1 Precision

Checked every profile in both NIM manifests directly, not just the GPU we use:

  • RFdiffusion-NIM: 7 profiles (one per GPU — L40S, A100, A10G×2, H100, GB200). Every one is fp16. No fp32 profile exists anywhere.
  • OpenFold3-NIM: 19 profiles across the full supported GPU list. Same story — all fp16.
  • OSS: checked the actual inference code (run_openfold predict --help equivalent, source inspection). Only precision-related option is --use_tf32 (a different thing — toggles Tensor Core matmul mode, not 16-bit precision). No fp16 option anywhere. RFdiffusion's own source explicitly disables autocast (@torch.cuda.amp.autocast(enabled=False)) on at least one module.
Matching precision exactly isn't achievable via configuration on either side. Confirmed, not assumed.

3.2 Version lag

Our OSS container is pinned to RosettaCommons/RFdiffusion commit b44206a (Aug 25, 2024, package v1.1.0). Compared directly against the live upstream repo: latest commit is from July 2026, 49 commits ahead. None of those 49 commits touch anything related to rng/seed/determinism. A full code search of the entire repository's history for the RNGs class NIM's sampler uses returns zero results, at any point, ever.

This isn't a version-lag problem. Even the latest open-source RFdiffusion doesn't have NVIDIA's injectable-seed mechanism. There is no newer OSS release to upgrade to that would close this gap.

3.3 NVIDIA's own "matches exactly" claim

NVIDIA's RFdiffusion-NIM benchmarking docs state: "when executed on the same architecture, the outputs match exactly... when evaluated across different GPU architectures, the mean RMSE... is below 0.64 Å," under "fixed random number conditions." Checked the page specifically for how this is achieved — environment variables, CUDA determinism flags, a script reference, anything. Nothing is disclosed. The claim can't be verified or replicated from the public documentation.

3.4 CUDA determinism flags

Checked whether OSS could be made more reproducible with torch.use_deterministic_algorithms(True) or CUBLAS_WORKSPACE_CONFIG (the mechanism NVIDIA's claim might rely on). Confirmed via source search: OSS RFdiffusion has zero references to either, anywhere in the package. Even if added, this wouldn't help close the NIM gap — it's a PyTorch-dispatch-specific concept, and NIM's compiled TensorRT engine doesn't go through PyTorch's kernel dispatcher at all.

Found a directly relevant precedent while investigating this: an open PR in RosettaCommons/foundry (for RFD3, a different/newer model, not the one in question here) documenting that "same seed → different designs" there was not a seeding bug — the RNG stream was byte-identical between runs. The real cause was a GPU reduction operation (scatter_mean/index_reduce_cuda) using non-deterministic atomics: repeated calls on byte-identical inputs returned different results depending on which GPU thread finished first. Since it ran once per denoising step, tiny differences compounded over the full trajectory into a different design. This is the same general class of problem later confirmed to likely explain our own result (Section 6).

4. First seed-matching attempt

Why: RFdiffusion generates from random noise — there's no "feed it an existing structure" shortcut the way there was for OpenFold3. Matching seeds was the only available lever to try to isolate precision's effect.

What we ran: OSS with inference.deterministic=true (design index 0), NIM with random_seed=0, identical target/contigs/hotspot.

First result: invalid, caught before being reported. Got 19.4 Å RMSD. Before trusting it, checked the actual .command.sh sent to the container — the seed had never actually been sent to NIM. Root cause: Groovy treats 0 as falsy, so ${random_seed ? ... : ''} silently skipped exporting RFD_RANDOM_SEED whenever the seed was 0. Fixed to ${random_seed != false ? ... : ''} and reran.

Corrected result: confirmed RFD_RANDOM_SEED="0" was genuinely present this time.

RMSD
Whole complex15.678 Å
Chain A (binder — the part RFdiffusion generates)18.660 Å
Chain B (target — fixed input, not generated)0.026 Å

Chain B's near-perfect match isn't evidence the seed worked — it's the unmodified input passing through unchanged on both sides, regardless of any seed.

5. Root cause, and the patch

5.1 Finding the actual mechanism

Read NIM's own model_utils.py directly: it constructs the sampler as model_runners.SelfConditioning(conf, rngs=RNGs(random_seed)) — a dedicated, scoped RNGs object passed explicitly into the sampler, not the global-state seeding OSS uses. Read rfdiffusion/rng.py itself from inside the NIM container (confirmed it's plain, unobfuscated Python): 15 lines, three isolated generator instances (random.Random(), np.random.RandomState(), torch.Generator()), each seeded independently. Marked NVIDIA-proprietary licensed, but the technique is generic enough to reimplement independently without copying it.

Traced every file that actually consumes this object (not guessed — grepped NIM's entire package, then diffed each hit against OSS's version to confirm it's genuinely wired into the call path our pipeline uses):

FileRole
rfdiffusion/rng.pyNew — the RNGs class, independently reimplemented
rfdiffusion/diffusion.pyTwo classes gain optional torch_rng/np_rng, used in torch.normal/np.random.* calls
rfdiffusion/inference/utils.pyget_next_ca and Denoise gain torch_rng; sampler_selector threads rngs through
rfdiffusion/contigs.pyContigMap gains py_rng (defaults to the random module itself when unset — same method names, no ternaries needed at call sites)
rfdiffusion/inference/model_runners.pySampler.__init__ gains rngs=None, threaded into Diffuser/ContigMap/Denoise/PotentialManager construction
rfdiffusion/potentials/potentials.py, manager.pyConfirmed not dead code on closer inspection — torch_rng is genuinely threaded through 2 call sites in model_runners.py; patched to match
scripts/run_inference.pyConstructs RNGs(seed) from a new, additive inference.rng_seed config field; falls back to today's exact behavior when unset

Confirmed out of scope: BlockAdjacency/ScaffoldedSampler (a different design mode our pipeline never uses).

Design principle throughout: fully additive. rngs=None is the default everywhere; every patched call site falls back to the exact pre-patch behavior (PyTorch's own generator=None semantics are identical to not passing a generator at all) unless the new seed is explicitly requested. Nothing changes for any existing caller.

5.2 Building and verifying the patch

All 8 files syntax-checked with py_compile before building. Built a new Docker image layering these patches on top of the base RFdiffusion image, with local, interactive import tests confirming the new RNGs class and updated function signatures worked correctly.

6. Two real infrastructure bugs found while testing (and how each was diagnosed)

6.1 Bug: ModuleNotFoundError: No module named 'rfdiffusion.rng'

The patch appeared to work in an interactive sanity check, then failed on the real AWS Batch run. Root cause: /app/RFdiffusion is not actually on sys.path — the interactive test only worked because its working directory happened to be /app/RFdiffusion, letting Python's implicit cwd-relative import resolve there by coincidence. At real runtime, Nextflow invokes the script by absolute path from its own work directory, so that coincidence doesn't hold — Python falls through to a completely separate, unpatched copy of the package in dist-packages. Verified all 7 source files were byte-identical between the two locations before patching both; rebuilt (v2), confirmed the fix by testing the import from a different working directory this time, not the one that gave the false positive.

6.2 Bug: Batch's own wrapper script passed as a literal CLI argument

New failure: run_inference.py: error: argument --cfg/-c: invalid choice: '<the entire Batch task wrapper script>'. Root cause: the patch image was built FROM the raw upstream ghcr.io image, which still has its ENTRYPOINT set (["python3", "/app/RFdiffusion/scripts/run_inference.py"]). Our actual production ECR image has this cleared (null) specifically for AWS Batch compatibility. With the entrypoint still set, Docker concatenates ENTRYPOINT + Batch's own CMD, so the entire task wrapper script was appended as a literal argument to Hydra's CLI parser instead of being executed as a shell script. Verified all 7 source files were byte-identical between the raw upstream image and our production ECR image first, then rebuilt FROM the correct base (v3), confirmed entrypoint was null this time.

6.3 Minor: Hydra strict-config rejection

Could not override 'inference.rng_seed' — Hydra's strict mode rejects setting a key that isn't already defined in base.yaml unless prefixed with + (its syntax for adding a new key rather than overriding an existing one). Fixed: inference.rng_seed=0 → +inference.rng_seed=0.

7. Final, verified result

Before trusting the result, confirmed both sides genuinely received the seed: OSS's resolved config showed rng_seed: 0; NIM's actual .command.sh showed RFD_RANDOM_SEED="0".

RMSD
Whole complex12.013 Å
Chain A (binder — generated)18.322 Å
Chain B (target — fixed input)0.030 Å
Essentially unchanged from the original, unpatched result (18.66 Å). The patch is correctly built and verifiably active on both sides — and it made no meaningful difference.

8. Conclusion

The RNGs-class mismatch was real and is now fixed, but it was necessary, not sufficient. The most likely remaining explanation, consistent with the unrelated foundry PR found in Section 3.4: RFdiffusion runs 50 sequential denoising steps, each feeding on the previous step's output. Even with byte-identical random draws, small numerical differences between NIM's compiled fp16 TensorRT kernels and OSS's PyTorch eager-mode execution would compound step-over-step across all 50 iterations into a completely different final structure. That's a fundamentally different problem from seeding, and not fixable by RNG alignment alone — closing this gap further would mean reconciling the two implementations' numerical kernels directly, which is a much larger, separate undertaking with no guaranteed payoff.

Recommendation: close this investigation here. Rely on the unpaired, N≈20-30 design statistical comparison (Mann-Whitney U on a locked primary metric) for assessing RFdiffusion specifically — this result confirms that approach is a necessity, not just a convenient choice, for this model.
